## 2. Scope and closure rule

**Scope.** Design section 19 defines WP-00 as: "Bind current repository, generated contracts, native targets, auth/client boundary, storage, update owner and deployment matrix", with the completion evidence "Binding ledger completed; exact deviations recorded without replacing accepted authority." Design section 22 lists 15 bindings. This ledger gives one row per binding (section 4), then the supporting facts (section 5), a deviation register against design section 2.2 (section 6), and open decisions and cross-repo owners (section 7).

**Closure rule.**

1. WP-00 is closed by this ledger being complete and honest. All 15 section-22 rows are present, each with a status, exact repository evidence and the gap.
2. WP-00 binds current truth. It records gaps. It does not close them. A gap in a row is work for the package named in that row's owner column, not work done here.
3. This ledger does not replace or amend accepted authority: existing application contracts, ADRs, migration allocations and release process documents stay authoritative. Where the design and an accepted contract differ, the difference is recorded in the deviation register (section 6) and left for the owning package to resolve with concrete evidence, as design section 19 requires.
4. A row marked bound or bound-with-deviation says the current repository mechanism is identified. It does not say the design requirement is met.
5. No row, and no sentence in this ledger, is evidence of complete-solution acceptance. Design section 22 says a partial delivery wave "cannot be labelled the complete solution". Gates in design section 20 are untouched and unrun.

**Status vocabulary.**

| Status | Meaning |
| --- | --- |

| Bound with deviation | A repository mechanism exists and is identified, but it differs from, or only partly covers, what the design requires. The deviation is stated. |
| Unbound this repo | This repository would own the capability by the design or by its ownership rules, but no implementation or contract for it exists yet. |
| Cross-repo | The deciding owner or artefact is outside this repository. This repository records only its own half and the dependency. |

## 3. Statement on migration 0069 and the document-intake modules

Migration `0069_document_intake.sql` and the modules `packages/omnivia-core-runtime/src/omnivia_core_runtime/storage/document_intake.py` and `packages/omnivia-core-runtime/src/omnivia_core_runtime/service/document_intake.py` are a **partial implementation of WP-01 and WP-02**. They are **not proof of complete native intake**.

What they are, from the files themselves:

- Migration 0069 adds seven tables (`omnivia_documents`, `omnivia_document_captures`, `omnivia_document_capture_retention`, `omnivia_extraction_profiles`, `omnivia_extraction_revisions`, `omnivia_extraction_results`, `omnivia_document_heads`) and their guard triggers. It is allocated as number 69, owner "Evidence Runtime", state `candidate`, `accepted_commit: null` (`contracts/migrations/v1/allocations.json`).
- The service module is described in its own docstring as "a maintenance path in the shape of `service/source_capture.py`, not an application operation", "nothing here is reachable over the application catalogue", and "this slice ships no format adapters, OCR, folder monitoring, native bookmarks or retrieval projection". Running an extractor is the caller's job: `reprocess_captured_copy` takes the extractor as a function.
- Capture takes a local `source_path` (`capture_document`) and reads it with the existing 16 MiB `source_capture` reader. It has no caller, principal, consent, native access or origin input.

What they are not:

- No application operation, schema, generated type, CLI command, MCP tool or Platform route exposes any of it. A search of `packages/*/src`, `contracts/`, `baseline/` and `scripts/` for `document_intake` and `omnivia_documents` finds only the migration, the two modules and the migration allocation file.
- No extraction adapter, OCR, retrieval projection, native handoff, monitoring, folder intake, subscription, tombstone or outbox exists in them.
- Their tests (`packages/omnivia-core-runtime/tests/phase3/runtime/test_document_intake.py`, `test_document_intake_migration.py`) prove the storage and service behaviour of that slice only. They are not design section 20 gates.

Design section 19 describes a first vertical slice (a file selected in Finder, captured unchanged, retrievable through Core and refreshable after a move or restart) as "a development checkpoint". Nothing on this branch reaches that checkpoint: there is no Finder route and no retrieval of a document capture.

## 5. Repository, contract, target, client, storage, update and deployment facts

### 5.1 Repository and validation

- Repository name `omnivia-core`; role: public core, graph, memory, contracts, schemas and public docs (`AGENTS.md`). It does not own the desktop shell, licensing, Harness implementation or paid Modules. `CLAUDE.md` adds that runtime-oriented implementations living here (memory, persistence, ingestion, search, graph assembly) are transitional local code, not a claim of long-term ownership.
- Changes land by pull request only; `./scripts/preflight` mirrors the `Core acceptance` workflow and must pass before a pull request is opened (`scripts/preflight`, `AGENTS.md`).
- Required checks on `main` (named in `AGENTS.md`): `Core acceptance` (`.github/workflows/core-acceptance.yml`, job name "Core acceptance", `ubuntu-latest`) and the three `Phase 2 platform` rows (`.github/workflows/phase2-platform.yml`, job name `Phase 2 platform (${{ matrix.os }})`, matrix `ubuntu-latest`, `macos-latest`, `windows-latest`). Neither the job names nor that matrix may change.
- The Swift companion is built and tested only on the macOS row of that matrix. The step is a no-op on the other two rows. The macOS runner image and Xcode version were not inspected for this ledger.
- Python: 3.11 or newer for all five packages.
- Local toolchain evidence only, gathered on the machine where this ledger was written: Swift 6.4, default target `arm64-apple-macosx27.0.0`, host macOS 27.0 on arm64. This is local-machine evidence. It is not support-matrix evidence: it says nothing about which macOS versions or architectures are supported, built or qualified, and the CI runner image and its Xcode version were not inspected.
